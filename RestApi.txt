A REST API (Representational State Transfer Application Programming Interface) is a set of rules that allows different applications to communicate with each other over the web using HTTP methods. It’s a standard for building web services and is widely used in modern web development.

Here’s a comprehensive breakdown of REST APIs, covering everything an interviewer might ask:

1. Core Concepts of REST API
a. Resources

In REST, everything is considered a resource, such as users, products, orders, etc. Each resource is identified by a unique URL (Uniform Resource Locator).
Example: A product might have the resource /products/123, where 123 is the product ID.

b. HTTP Methods
REST uses standard HTTP methods to perform actions on resources. The four most commonly used methods are:

GET: Retrieve data from the server (e.g., fetch a product list).
POST: Create a new resource on the server (e.g., add a new product).
PUT: Update an existing resource (e.g., modify product details).
DELETE: Delete a resource (e.g., remove a product).
Other methods include PATCH (for partial updates) and HEAD (to retrieve metadata).

c. Statelessness

REST APIs are stateless, meaning each request from a client must contain all the information the server needs to fulfill that request. The server doesn’t store client session data between requests.

d. Client-Server Architecture

REST separates the concerns of the client and server:
The client is responsible for the user interface and making requests.
The server manages the business logic, databases, and the resources.

e. Uniform Interface

REST APIs follow a uniform interface between the client and the server, which simplifies and decouples the architecture. Key elements include:
Resource-based URIs: Every resource is identified using URIs (Uniform Resource Identifiers).
Manipulation via representations: Resources are manipulated by sending a representation (typically JSON or XML) of the resource to the server.

Self-descriptive messages:

 Each request and response contains enough information to describe how to process the message.
Hypermedia as the Engine of Application State (HATEOAS): A RESTful API response contains links to related resources to provide discoverability (this is an optional constraint).

2. API Endpoint Structure

a. Base URL

The Base URL defines the root address where your REST API is located.
Example: https://api.example.com

b. Endpoints

Endpoints are paths that represent specific resources or operations. They are appended to the Base URL.
Example: /api/products/123
/api/products → Represents all products.
/api/products/123 → Represents a specific product with the ID 123.

c. Example Endpoints:
javascript
Copy code
GET /api/products               // Fetch all products
GET /api/products/123           // Fetch a specific product with ID 123
POST /api/products              // Add a new product
PUT /api/products/123           // Update the product with ID 123
DELETE /api/products/123        // Delete the product with ID 123

3. HTTP Status Codes

REST APIs use HTTP status codes to indicate the result of an API request:

200 OK: Request succeeded.
201 Created: Resource created successfully.
204 No Content: Request succeeded, but no content to return (usually for DELETE operations).
400 Bad Request: The request was invalid or malformed.
401 Unauthorized: The user is not authenticated.
403 Forbidden: The user doesn’t have permission to perform the operation.
404 Not Found: The requested resource was not found.
500 Internal Server Error: Something went wrong on the server.

4. Data Formats

REST APIs typically exchange data in JSON (JavaScript Object Notation) format. However, XML is also sometimes used.
Example JSON Response:
json
Copy code
{
  "id": 123,
  "name": "Product A",
  "price": 100,
  "category": "Electronics"
}

5. CRUD Operations in REST
REST APIs map CRUD (Create, Read, Update, Delete) operations to HTTP methods:

Create → POST
Read → GET
Update → PUT or PATCH
Delete → DELETE
Example CRUD API for a product resource:

javascript
Copy code

  "name": "New Product",
  "price": 100,
  "category": "Electronics"
}

// READ
GET /api/products
GET /api/products/123

// UPDATE
PUT /api/products/123 {
  "name": "Updated Product",
  "price": 150
}

// DELETE
DELETE /api/products/123

6. REST vs. Other API Styles

REST: Stateless, resource-oriented, typically uses JSON over HTTP.
GraphQL: An alternative to REST that allows clients to query only the data they need, with a more flexible structure.

7. Versioning REST APIs
APIs change over time, so versioning is important to maintain backward compatibility. 
Example of versioned API: /api/v1/products
Common ways to handle versioning:

In the URL: /api/v1/products
In the Header: Accept: application/vnd.company.v1+json

8. Authentication and Authorization
REST APIs often require authentication (verifying who the user is) and authorization (verifying what they can do).

Token-based authentication: Most common method. Tokens (like JWT - JSON Web Tokens) are passed in headers.

Example:
javascript
Copy code
Authorization: Bearer <token>
OAuth: Another popular authentication standard for REST APIs, used for delegated access (e.g., logging in with Google or Facebook).

9. Rate Limiting

To prevent abuse or excessive load on servers, REST APIs often implement rate limiting.

Example: A client can only make 100 requests per hour. If they exceed this, they receive a 429 Too Many Requests response.

10. Pagination

When fetching a large set of resources, APIs typically implement pagination to break up data into smaller chunks.

Example:
javascript
Copy code
GET /api/products?page=2&limit=20
This would return the second page with 20 items per page.

12. Advantages of REST API

Simplicity: REST APIs use standard HTTP methods, making them easy to understand and implement.
Scalability: Statelessness allows servers to scale easily because they don’t need to store client context.
Flexibility: The separation of client and server enables different frontends (mobile, web) to interact with the same API.

13. Disadvantages of REST API

Over-fetching/Under-fetching: Sometimes, clients might receive more data than needed, or they might have to make multiple requests to get all the required data.
Statelessness: Can result in the need to include authentication tokens and other data in every request.

Statelessness in REST API means that each request from a client to a server must contain all the information needed to understand and process the request. The server does not retain any information (state) about previous requests from the same client. This makes each request independent, and the server treats every request as new.

Key Characteristics of Statelessness:

No client context is stored on the server: Each request must be self-contained, with the necessary data, such as authentication tokens or session details, sent with every request.

Simplifies scalability: Since the server does not need to maintain any state information, it becomes easier to scale.

Example of Statelessness
Imagine a shopping app where a user is retrieving their order history. The server does not store any session details about this user between requests.

Example Scenario:
Client Request (1st Request):

http
Copy code
GET /api/orders HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Here, the client sends an Authorization header with a token to identify the user. The server processes the request and sends back the user's order history.

Client Request (2nd Request):

http
Copy code
GET /api/orders/123 HTTP/1.1
Host: example.com
Authorization: Bearer <token>

In the second request to fetch a specific order, the Authorization token is sent again. The server has no memory of the previous request; it processes this request independently using the token provided.

Contrast: Stateful Example (Non-REST)

In a stateful system (like traditional server sessions), the server would keep track of the user's session, meaning the client would only need to authenticate once, and all subsequent requests would reference the saved session.

In RESTful APIs, statelessness simplifies the architecture but requires that clients send all necessary data, like authentication tokens, with each request.
